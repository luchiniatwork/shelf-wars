# Board Game Prototyping

## When to use / when not to use

Use this skill when the user needs to:
- Turn an idea or ruleset into a first playable build, or choose what fidelity to build at.
- Pick physical materials/tools, set up a data-merge card pipeline, or build boards, tiles, and tokens.
- Choose or set up a digital playtesting platform (TTS, Tabletopia, Screentop.gg, Playingcards.io).
- Package a print-and-play (PnP) or remote blind-test kit.
- Set up versioning/changelog discipline, or estimate component quantities before manufacturing exists.

Do NOT use this skill for:
- Running playtest sessions, feedback instruments, recruitment, kill criteria → `board-game-playtesting`.
- Final print specs, manufacturer quotes, compliance, freight → `board-game-manufacturing`.
- Rulebook authoring for the kit → `board-game-rules-writing`.
- What to change between builds (cost curves, probabilities) → `board-game-math-balance`.
- Sell sheets and pitching logistics → `board-game-publishing`.

## Core principles

1. **A prototype is a question-answering machine.** Name the question ("does the core loop produce interesting decisions?", "is 4p downtime tolerable?") before choosing materials. Fidelity follows the question, never the reverse.
2. **Never polish before the loop works.** Ugly-prototype doctrine (Jamey Stegmaier; Geoff Engelstein): polish breeds attachment, wastes iteration budget, and pulls tester feedback toward aesthetics instead of mechanisms.
3. **Minimum viable content.** Stegmaier: for a game planned to have 100 cards, design 10–20 up front — "just enough for the game to function." Build content breadth only after the loop survives strangers.
4. **Match fidelity to audience.** Peter Vaughan's four stages (League of Gamemakers): solo/close-friends build → game-design-night build → convention/Protospiel build → reviewer build. Each audience tolerates less temp material than the last.
5. **Table time beats noodling.** Community rapid-prototyping maxim: get a prototype on the table ASAP — a minute of table time teaches more than an hour of solitary noodling. Target idea → first playable in under a week.
6. **Physical first, digital for reach.** Stegmaier treats digital testing as strictly *secondary*: component size, table footprint, and fiddliness issues are obscured digitally. Re-verify physically before manufacturing.
7. **One source of truth: a spreadsheet.** Card content lives in CSV/Google Sheets; components are regenerated by data merge (nanDECK, Component.Studio) in minutes. Hand-editing 100 card files is how card text and rulebook drift apart.
8. **One variable per iteration, versioned and logged.** Early thrash is fine; once the core holds, each build changes one variable so effects are attributable. Every build has a version number, date, and changelog entry.
9. **Build for re-build speed.** Paper inserts in opaque sleeves over backing cards: a content change costs one reprinted sheet, not a new deck.
10. **Prototype usability is graphic design, not art.** Hierarchy of information (most-used value biggest), unambiguous icons, consistent visual language (League of Gamemakers, "Graphic Design: Prototyping Priorities"). Zero art is fine; ambiguity is not.

## How to apply it

### A. Stage gates — what to build and when to advance

| Stage | Question it answers | Invest | Exit criteria |
|---|---|---|---|
| 1. Proof-of-concept (solo sim) | Is the core loop functional? Fun to operate? | ~$0: index cards, hand-scrawled boards, cannibalized bits | You can run a full session solo controlling 2–3 seats without rules collapsing |
| 2. Ugly functional | Does it survive other humans? Where does it drag? | ~$20–50: sleeve+insert cards, label-paper boards, bulk cubes/dice | Core loop proven in guided tests; changes still weekly; no one confused by components |
| 3. Polished prototype | Will strangers choose to play? Is it blind-testable? | Data-merge pipeline, icon set, POD or high-quality home copies (~$16–80/copy documented), ≥2 copies | Legible without you present; component counts stable; ready for blind waves |
| 4. Pitch / PnP-grade | Can someone evaluate it with zero help from you? | Near-final rulebook, finalized component manifest, clean UI, boxed, PnP kit | A reviewer/publisher unboxes and plays unaided; card text matches rulebook |

Never skip gates; never invest above the current gate. Publisher pitches need **thoughtful graphic design, not professional art** (Stegmaier) — publishers redo art but judge usability.

### B. Physical build recipes (fast paths)

- **Cards L1:** index cards, marker, done (~$3/100 cards).
- **Cards L2 (the workhorse):** print paper inserts → cut → slip into opaque sleeves (Dragon Shield Matte, UltraPro, KMC — avoid penny sleeves, they rip mid-test) over backing cards (old MTG commons or poster board) for shuffleable stiffness.
- **Cards L3:** print-on-demand (The Game Crafter, MakePlayingCards) once counts stabilize.
- **Boards:** cardstock + scotch tape folding board (League of Gamemakers method — cheap, portable, replaceable), or full-sheet label paper on 0.022–0.030″ chipboard; blank boards from education stores + low-tack label paper for repositionable elements.
- **Tiles/counters:** label paper on chipboard, cut with a $20 scrapbooking trimmer.
- **Bits:** bulk wooden cubes/meeples/dice (~$10/100 meeples, ~$10–15/100 d6), education-store supplies (Unifix cubes, fake money), cannibalized games; sort into a bead-organizer bit box.

Full recipes, BOM with costs, and pipeline setup: load `references/physical-materials.md`.

### C. Data-merge pipeline (the iteration engine)

1. Spreadsheet: one row per card, columns = name, type, cost, rules text, icon, count, version.
2. Generator: nanDECK (free, CSV-driven scripting; exports print PDFs *and* Tabletop Simulator saves directly), Component.Studio (~$9.99/mo at research time; Google Sheets → components; pushes to The Game Crafter and TTS), Inkscape (free), or Affinity Designer + Publisher (one-time purchase; Publisher does data merge). Stegmaier uses InDesign + HP color laser + Cutterpillar trimmer.
3. Rebuild loop: edit rows → re-export → reprint only changed inserts.

### D. Digital platforms — quick decision

| Platform | Cost | Tester friction | Best at | Watch out |
|---|---|---|---|---|
| Tabletop Simulator | $19.99/seat (Steam) | Install + purchase each tester | Physics, complex games, Lua automation | Cost/install barrier; build learning curve |
| Tabletopia | Free tier (browser) | Link join, free for testers | 3D presentation, no-code setup | Clunky mid-game edits; free-tier limits |
| Screentop.gg | Free (browser) | Zero: no accounts, mobile OK | Fast 2D iteration, max accessibility | No scripting; components locked mid-session |
| Playingcards.io | Free (browser) | Zero: no accounts | Card-first games; automation buttons | Weak for non-card components; small text; no voice |

Platform setup workflows, scripting notes, and migration triggers: load `references/digital-platforms.md`.

### E. Versioning & change discipline

- Version every build (`v0.4.2`), date every file; archive old versions — you *will* revert.
- Changelog per build: version | date | hypothesis | **one** changed variable | result.
- Stage 1–2 tolerates multi-change thrash; from stage 3, one major system per version.
- Never tweak a build a publisher/reviewer is currently evaluating — branch a copy instead (MVP Board Games).
- Keep the component manifest in the same spreadsheet as card data so counts and content version together.

### F. Component quantity estimation (before manufacturing exists)

- Maintain a manifest: item | dimensions | qty/game | per-player scaling | notes.
- Press-sheet sanity check (Panda GM): 63×88 mm poker cards fit 54/sheet, 44×67 mm mini fit 84/sheet — card counts near sheet multiples cost less later.
- Bits: (max simultaneous need per player × max player count) + ~10% spares.
- Punchboard constraints to respect even in prototypes: tokens ≥ ~8×8 mm, ≥6 mm between dielines [unverified — attributed to Panda GM, no citable spec sheet; treat as community ballpark] — keep prototype tokens ≥10 mm so the design survives manufacturing.
- Full component specs and costing → `board-game-manufacturing`.

### G. When to move physical → digital (and back)

- Go digital for: remote/blind waves, balance loops needing many repetitions, testers who can't print, geographic spread.
- Stay/go back physical for: tactility-dependent play (dexterity, stacking), table-footprint realism, component-usability testing, final pre-manufacturing verification.
- Rule: any balance conclusion drawn digitally must be spot-checked on the physical build before committing manufacturing specs.

### H. Remote-tester accessibility

- Default to zero-install, link-join platforms (Screentop.gg, Playingcards.io, Tabletopia) unless physics/scripting justify TTS's $19.99 + install per tester.
- Always ship: PnP PDFs in A4 **and** US Letter, a low-ink variant, an explicit household-supplies list (dice, pawns, scissors), and a feedback form with a version field.
- Test your own share link in an incognito window before sending; include a 5–10 min setup expectation in the invite.
- PnP packaging spec: load `references/pnp-kit-checklist.md`.

## Common pitfalls

- **Premature polish:** art and graphic polish before the loop works → attachment, change-aversion, and testers critiquing aesthetics instead of mechanisms.
- **Content over-scoping:** designing all 100 cards before the loop survives stage 1; most of it is discarded.
- **Hand-maintained card files:** no spreadsheet → card text and rulebook silently diverge; blind-test data becomes noise.
- **Five-change rebuilds:** can't attribute effects; balance regressions ship undetected.
- **Penny sleeves:** rip during shuffling mid-session; use matte branded sleeves.
- **Digital-only validation:** a game balanced in TTS can still fail physically (footprint, fiddliness, component legibility).
- **Mid-wave rebuilds:** changing files while blind testers are active → testers on different versions, garbage data. Batch changes between waves.
- **Single-copy risk:** your only prototype is in the mail → development stalls. Keep ≥2 once pitching.
- **Tester-friction blindness:** requiring installs, accounts, or purchases cuts remote participation; match platform cost to tester commitment.
- **Prototype only you can operate:** if the game can't be played without the designer present, it isn't ready for blind testing or pitching.
